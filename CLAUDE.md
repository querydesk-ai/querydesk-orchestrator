# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**QueryDesk orchestrator** — the Python/FastAPI half of an internal AI service desk for an insurance
company. It answers questions the knowledge base covers (citing the source article) and turns action
requests into correctly categorised Service Requests (SRs) it tracks to closure.

The authoritative spec is `../SR Resolution Bot — Final PRD & 10-Day Roadmap.md`. **Read it before
making design decisions** — it supersedes the older "Phase 0 / Phase 1" framing that earlier versions
of this repo used. The current task breakdown lives in [docs/task.md](docs/task.md); the next day's
design is in [docs/plan-day-8.md](docs/plan-day-8.md).

QueryDesk is two services behind one contract:

| Repo | Contents | Owner |
| --- | --- | --- |
| `querydesk-orchestrator` | **this repo** — FastAPI, RAG, router, decision layer, Celery, chat page | Orchestrator team |
| `querydesk-ticketing` | Spring Boot 3 / Java 21 ticketing service, migrations, webhook outbox | Ticketing team |
| `querydesk-docs` | PRD, OpenAPI contract, `categories.json`, eval set | Both |

**Contract first:** no endpoint or field change without a PR in `querydesk-docs` approved by the
other person. The orchestrator never reaches into the ticketing service's database — only its API.

## Commands

The package uses a `src/` layout (`src/querydesk`) and is managed with **uv**: `uv sync` builds
`./.venv` from `uv.lock` (Python from `.python-version`, dev group included). pytest also sets
`pythonpath = ["src"]`, so tests import the package without an install.

```bash
uv run pytest -q                            # full suite; offline, no API key

uv run scripts/check_services.py            # Qdrant / Redis / Postgres reachability
uv run scripts/migrate.py                   # apply migrations/*.sql to Neon (--status to list)
uv run scripts/ingest.py --recreate         # re-index data/kb into Qdrant
uv run scripts/eval_run.py                  # eval set vs live services + decision layer -> eval/results/
uv run scripts/eval_report.py               # proposals + docs/eval-report-latest.md (never edits config)
uv run scripts/eval_report.py --out docs/eval-report-vN.md --title "Eval report vN"   # publish one
uv run --with psutil scripts/latency_spike.py   # local embedding models vs qwen3 (in-memory Qdrant)

# Stand-in for the ticketing service (contract v1.1), until it is deployed:
uv run uvicorn tests.fakes.fake_ticketing:app --port 8081
TICKETING_BASE_URL=http://127.0.0.1:8081 uv run uvicorn querydesk.main:app --reload

uv run uvicorn querydesk.main:app --reload   # chat page at http://127.0.0.1:8000/

# Status notifications (Day 7). WEBHOOK_SECRET must match on both sides. Windows needs --pool=solo.
STAND_IN_WEBHOOK_URL=http://127.0.0.1:8000/webhooks/sr-status uv run uvicorn tests.fakes.fake_ticketing:app --port 8081
uv run celery -A querydesk.worker worker --pool=solo -l info --without-gossip --without-mingle --without-heartbeat
uv run celery -A querydesk.worker beat -l info     # reconcile every reconcile_interval_s
uv run celery -A querydesk.worker call querydesk.reconcile   # one reconcile now
```

Docker (`Dockerfile` targets `runtime` and `stand-in`; `compose.yaml` runs api, worker, beat, a
local Redis, and with `--profile stand-in` the fake ticketing service). Inside compose,
`REDIS_URL` is the local container and `TICKETING_BASE_URL` comes from
`DOCKER_TICKETING_BASE_URL` (default `http://ticketing:8081`), never `.env`'s host address.

```bash
docker compose --profile stand-in up --build
docker compose run --rm api python scripts/migrate.py
docker build --target runtime -t querydesk-orchestrator .   # CI builds both targets
```

Dependencies live in `pyproject.toml` + `uv.lock` only — no `requirements.txt`. Commit `uv.lock`
with every dependency change; CI runs `uv sync --locked` and fails if it is stale.

The test suite must stay fully offline — mock Fireworks with `respx`, monkeypatch the embed and
search functions. A test that needs a live API key or a live Qdrant does not belong in `tests/`.

## Architecture

Request flow for `POST /chat`: if a slot-filling conversation is open in Redis the message fills
missing fields (no embedding or search); otherwise hybrid retrieval returns top KB chunks and the router returns the top two
categories. The decision layer picks one decision + `resolution_type`. Answers are generated by
Fireworks from the retrieved chunks; SRs go to the ticketing service with an idempotency key.
Everything after SR creation is async (webhook → Redis → Celery).

### Module conventions

- **One module owns each external dependency**, and nothing else may talk to it directly:
  `services/llm/fireworks.py` (LLM + embeddings), `services/llm/local_embed.py` (the local
  fastembed dense model), `services/retrieval/qdrant_store.py` (vector
  search), `services/retrieval/sparse.py` (BM25), `services/ticketing/client.py` (the ticketing
  service), `services/state/redis_store.py` (Redis), `services/state/postgres_store.py` (the
  orchestrator's Neon DB), `services/llm/jev.py` (Jev, via JevStation),
  `services/messaging/meta.py` (Meta's WhatsApp Cloud API), `services/messaging/twilio.py`
  (Twilio's WhatsApp API).
  The Celery app is `src/querydesk/worker.py`; its tasks are thin and call `services/` code.
  Each raises a subclass of `UpstreamError` (`core/errors.py`), and the routers map that whole
  family to HTTP 502 in one place.
- `services/catalog.py` is the only app-code reader of `categories.json` (invariant #3); ask it for
  a category's name, approval rule or required fields.
- **`core/config.py` is the only reader of the environment.** Nothing else touches `os.environ`;
  import the shared `settings` instance instead of re-instantiating `Settings`.
- `services/pipeline.py::handle_message()` is the whole `/chat` flow. It first loads
  `conversation.load(user_id)`; an open conversation goes to `_continue()` (cancel →
  `extract_follow_up()` on **the reply only** → merge, where a stated value may correct a collected
  one (`corrected:` override) → `engine.complete_sr()` → `_advance()`: raise / ask again / escalate
  after `conversation_max_follow_ups`). A status question (`signals.classify().is_status`) is decided
  **before** any embedding or search — rule 1 needs only the intent — and answered by
  `services/status.py` (open SRs, or one SR by number; someone else's SR reads exactly like a
  missing one). A reply that states no field is decided as a fresh message
  (`_decide_fresh()`, no side effects): a rule-5 `ESCALATE` means it made no sense on its own, so
  it counts as an unhelpful follow-up (`unanswered:` override); anything else clears the
  conversation and is acted on normally. The fresh flow: embed once → `rag.retrieve()` +
  `router.route()` concurrently → `signals.classify()` → `engine.decide()` → act (generate / create
  SR / ask for fields and open a conversation / escalate) → one `querydesk.decision` log line with
  its `turn` (PRD F10). `_log()` also hands the same record to `postgres_store.record_decision()`
  as a background task (held in `_decision_writes`, awaited by `drain_decision_writes()` on
  shutdown): it never adds latency and a failed write is only a warning; no `POSTGRES_DSN` means
  no write. A bare "cancel" with nothing open is answered without a search or a record.
  The route in `api/routes/chat.py` stays a thin adapter.
- Before asking for details **and** before raising, `_already_open()` checks
  `ticketing.list_open_srs()`: one open SR per user and category (F5), reported as `RAISE_SR` with
  the existing `sr_id` (like an idempotent replay). An escalation at the follow-up cap records the
  conversation's category, fields and transcript, and its reply names what's missing. Raised SRs and escalations
  are recorded in `sr_requests`; a failed write never loses the SR, and a failed escalation write
  falls back to "contact the desk" instead of "flagged".
- `services/conversation.py` owns `conversation:{user_id}`. Redis down means single-turn, never a
  500: `load` returns None, `save`/`clear` are no-ops.
- `services/rag.py` has `retrieve()` (search only — the decision needs the score first) and
  `generate()` (the grounded answer). Routing rules do not go in it.
- `services/retrieval/query.py::embed_query_vectors()` embeds a message **once**; pass the result to
  both `rag.retrieve(vectors=...)` and `routing/router.route()`. Embedding is the slowest step (~2 s),
  so dense vectors are cached in Redis (`qemb:{model}:{sha256}`); a Redis failure is a cache miss,
  never an error. `eval_run.py` turns the cache off so it measures real latency.
- `services/routing/router.py` reports the top-two categories and whether it is confident; it never
  decides answer-vs-SR — that is the decision layer's job.
- `services/decision/`: `signals.py` (rule-based is-action / is-status), `extraction.py` (one LLM
  call for required fields, **SR path only**; absent or unparseable = missing, never guessed;
  `extract_follow_up()` reads only the latest reply, the original request is context, and every
  value must appear in that reply (`_grounded()`) — never extract from a joined transcript, the
  model copies sentences from it into fields. First-message extraction is not grounded: a
  categorical reading like `change_type: "firewall change"` is fair there, and the eval measures it),
  `rules.py` (rule 6 from `data/decision_rules.json`, tighten-only, validated against the catalog),
  `engine.py` (`DecisionEngine` interface + `RuleEngine`, chosen by `decision_engine`).
- `services/notifications/`: `signing.py` (HMAC-SHA256 hex of the raw body in `X-Signature`;
  empty `WEBHOOK_SECRET` rejects all) and `notify.py` — `handle_status_change()` is the **only**
  write path for a status notification, used by both the webhook task and `reconcile()`. It is
  idempotent: `notifications` is unique per `(sr_id, status)`, and `sr_requests.status` only moves
  to a higher `ticketing.STATUS_RANK`. PENDING is never notified. `POST /webhooks/sr-status`
  (`api/routes/webhooks.py`) only verifies, validates and enqueues — 202, or 503 if the broker
  can't take it so the sender retries. Celery tasks run coroutines on one loop per worker process
  (`worker._run`), never `asyncio.run()`: the asyncpg pool and clients are loop-bound.
- `GET /notifications` / `POST /notifications/read` (`api/routes/notifications.py`) read the
  table the notify task writes; marking read is scoped by `user_id`. There is no login in v1:
  `user_id` is a parameter everywhere, as on `/chat`. `GET /` serves the one-file chat page
  (`src/querydesk/static/index.html`, vanilla JS, no CDN), which polls unread notifications every
  10 s and marks them read once shown.
- **WhatsApp** ([docs/whatsapp.md](docs/whatsapp.md)) is a private one-to-one chat, never a
  broadcast or group, through `whatsapp_provider` `meta` (default, free test number) or `twilio`;
  off unless that provider's settings and `whatsapp_id_secret` are set. Provider-neutral code is
  `services/messaging/whatsapp.py` (identity, `send()` dispatch) and `text.py` (formatting);
  numbers are E.164 between modules. `/webhooks/whatsapp` (`api/routes/whatsapp.py`): GET is
  Meta's verify-token check; POST verifies the provider's signature (Meta: HMAC-SHA256 of the raw
  body; Twilio: against `whatsapp_public_url`, never the request's own URL), drops a repeated
  message id, queues `querydesk.whatsapp_message` and answers at once.
  The worker runs `services/messaging/inbound.py::reply_to()`, the same `handle_message()` as
  `/chat`, and must `drain_decision_writes()` before the task returns. That task never retries
  (a rerun could advance a conversation twice); `whatsapp_send` retries provider failures. The
  pipeline only ever sees `user_id_for(phone)` (`wa-` + HMAC): **a phone number never reaches the
  ticketing service, logs or `decision_logs`**; only `whatsapp_users` holds it. Status updates
  reach WhatsApp from `handle_status_change()` after a *new* notification is written, so the
  existing dedupe also prevents double messages.
- Use the **async** Qdrant client (`AsyncQdrantClient`). The `/chat` path is async and the sync client
  would block the event loop. `fastembed` is sync and CPU-bound, so call it through
  `anyio.to_thread.run_sync` from async code.

### Invariants that are easy to break

1. **Confidence comes from the top *dense* cosine similarity, never from the fused score.**
   Qdrant's RRF fusion returns rank-based scores, so a threshold on a fused score is meaningless
   (PRD Gap #2). `hybrid_search()` therefore returns *both*: the fused hits decide **what** the LLM
   sees, the dense score decides **how confident** we are. Never thread a fused score into a
   confidence threshold.

2. **`qwen3-embedding-8b` is asymmetric.** (The PRD's `nomic-embed-text-v1.5` is no longer served
   on Fireworks.) Documents are embedded **as-is**; queries are wrapped in `QUERY_INSTRUCTION`
   (`Instruct: … 
Query: <text>`). Always use `embed_documents()` / `embed_query()`, never
   `embed_text()` on raw text, and never add the old `search_document:` / `search_query:` prefixes.
   It emits 4096 dims (`embed_dim`). Changing the model means re-running `ingest.py --recreate`;
   `ensure_collections()` refuses to start against a collection of the wrong size.
   Dense embeddings go through `services/retrieval/embedding.py`, which dispatches on
   `embed_backend`: `fireworks` (default) or `local` (bge-base, 768 dims, queries prefixed with
   `LOCAL_QUERY_PREFIX`, documents as-is; own collections `*_bge768`). bge was trialled and **not
   adopted** — `docs/embedding-trial.md`. The query cache keys on `settings.embed_model_id`, so the
   backends never share vectors.

3. **`data/categories.json` is the single source of truth** for the 10 categories — ids, approval
   rules and required fields — shared with the ticketing service. Never hardcode a category id,
   required-field list or approval flag anywhere in the code.

4. **Thresholds are calibrated, not guessed.** `confidence_high` / `confidence_mid` /
   `router_min_score` come from the 60-query eval set (`eval/eval_set.jsonl`,
   `docs/eval-report-v0.md`). Don't tune them by hand against a single query: change the eval set,
   re-run `eval_run.py` + `eval_report.py`, and record the decision in the report.

5. **Qdrant's sparse vector needs `modifier=models.Modifier.IDF`** to score BM25 correctly. Omitting
   it is silent — search still "works", just badly.

6. **Never answer ungrounded.** No retrieval hits means `MANUAL_ESCALATION` with a fixed reply and
   **no LLM call** — not a best-effort guess.

### Resolution types and decisions

`resolution_type` is one of `RAG`, `AUTO_SR`, `MANUAL_ESCALATION`. The decision layer (PRD Day 4)
emits one of `ANSWER`, `ANSWER_WITH_DISCLAIMER`, `COLLECT_DETAILS`, `RAISE_SR`, `ESCALATE`,
`STATUS_LOOKUP`, first match wins (rules in `services/decision/engine.py`); `CANCELLED` is the
pipeline's, for a cancelled conversation. Only add an enum value when the code can actually emit it.
Rule 6 also applies to fields collected over several turns (`complete_sr()`).

**An action request must never be answered with an article** — the PRD's most important failure.
Retrieval scores can't prevent it (eval: 86% of action requests clear `confidence_high`), so rules
2–3 require `signals.classify()` to say *not an action*. Any change to `signals.py` must keep
`tests/unit/test_signals.py` green and be re-measured with the eval (target ≤ 5%).

The decision layer ships as a **rule engine behind an interface**. Jev was measured against it on
Day 5 (`docs/jev-notes.md`): rules 97% vs Jev 91% routing accuracy, and Jev takes 3.5–7 s per call
through JevStation, so **the rule engine is the default and Jev is not on the `/chat` path**.
`TYPESAFE_API_KEY` is a JevStation key; every evaluation spends a limited credit, so never call Jev
from tests (mock it with respx) and run `scripts/jev_compare.py` with a `--budget`. Its cache under
`eval/results/jev_cache/` makes re-runs free.

The contract is `openapi.yaml` in `querydesk-docs` (v1.1; querydesk-docs PR #1). Until the
ticketing service is deployed, `tests/fakes/fake_ticketing.py` implements it for tests and
manual runs: idempotency key, 400 on an unknown category, the paginated `GET /sr` envelope (which
`client._list()` reads page by page and also accepts as a plain list), and integer `sr_id`s in
webhooks (`SRStatusEvent` coerces them to strings).

## Data stores

Each service owns its own Neon Postgres database; they share nothing but the API contract.

- **Qdrant**: `kb_chunks` (named vectors `dense` + `bm25`) and `categories` (dense only).
- **Postgres** (`sr_orchestrator`): `sr_requests` (Day 6, `migrations/001_sr_requests.sql`),
  `notifications` (Day 7, `002_notifications.sql`), `decision_logs` (PRD F10,
  `003_decision_logs.sql`), `whatsapp_users` (`004_whatsapp_users.sql`). Schema changes are plain SQL files in `migrations/`,
  applied in name order by `scripts/migrate.py` and tracked in `schema_migrations` — never edit an
  applied one. Only `services/state/postgres_store.py` connects from app code.
- **Redis**: reached over `REDIS_URL` (`rediss://`, the native protocol to Upstash, never its REST
  API), only through `services/state/redis_store.py`. Holds the query-embedding cache
  (`qemb:*`), `conversation:{user_id}` slot-filling state (`conversation_ttl_s`, 30 minutes;
  `services/conversation.py`), the reconciliation watermark (`reconcile:since`), seen WhatsApp
  messages (`wa:msg:{MessageSid}`) and the Celery broker.
  Run dev workers with `--without-gossip --without-mingle --without-heartbeat` — an idle Celery
  worker will otherwise burn the Upstash free-tier command quota.

## Secrets

`.env` is gitignored and holds live credentials; `gitleaks` runs in CI. Never commit it, never paste
key values into code, logs or test fixtures. `FIREWORKS_API_KEY` is required for ingestion and the
answer path; `TYPESAFE_API_KEY` (JevStation) is used only by `scripts/jev_compare.py`; `WEBHOOK_SECRET` is shared
with the ticketing service. `META_APP_SECRET` / `TWILIO_AUTH_TOKEN` verify the WhatsApp provider's
signatures; `WHATSAPP_ID_SECRET` keys the `wa-` user ids, so changing it re-identifies every user.
